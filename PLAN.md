# SRE Agent — Deep Plan

*Project launched 8 November 2026. Owner: Abraham Kakooza. Repository: github.com/KakoozaJerry/sre-agent (public). This plan is refined hourly; the progress log at the bottom is the source of truth for what has actually been done.*

## 1. Vision

An open-source, autonomous Site Reliability Engineering agent that detects production incidents, triages them with evidence, and helps remediate them under strict, human-approved guardrails — then writes the postmortem and learns from it.

Most "AI SRE" demos stop at a chatbot that summarises alerts. This project aims higher: a working agent with a real tool layer, a real safety model, and a real evaluation harness, developed in the open. It is both a portfolio artefact and a research testbed for agentic AI in production operations: agent runtimes, harnesses, evaluation, and control — the same ground as Abraham's agentic AI red/blue teaming research direction.

## 2. The problem

On-call SRE work has a repeatable shape: an alert fires, someone pages through dashboards, correlates metrics, logs and recent deploys, forms a hypothesis, tries a known remediation, and verifies recovery. The slow parts are rarely the fix — they are detection-to-diagnosis time, context gathering across five tools, and the 3 a.m. cognitive load. Industry data consistently shows most incident time is spent diagnosing, not fixing.

An agent is well suited to the diagnosis half and to executing bounded, pre-approved remediations — if, and only if, it can be trusted not to make things worse. That trust problem is the actual product.

## 3. Design principles

1. **Safety before autonomy.** Autonomy is earned in tiers (Section 6). Every mutating action is classified, bounded, reversible where possible, and written to an immutable audit log before it runs.
2. **Evidence or it didn't happen.** Every diagnosis claim must cite the query that supports it (metric, log line, event). The agent never asserts a cause it has not observed.
3. **Telemetry is untrusted input.** Logs, alert text and web pages can contain prompt injection. All tool output is treated as data, never as instructions. This is a first-class threat model, not an afterthought, and it is where the red-teaming research feeds the engineering.
4. **Least privilege by construction.** Read-only credentials by default; write capability is scoped per tool, per environment, and granted per action tier.
5. **Evaluation-driven development.** No capability ships without a chaos-scenario test that measures it. Unsafe-action rate target: zero, gated in CI.
6. **Model-agnostic core.** The reasoning loop talks to a pluggable model backend (hosted APIs or local models) behind one interface, so the harness outlives any single model.
7. **Boring, operable software.** The agent itself must be deployable, observable and debuggable like any production service: structured logs, its own health endpoint, a kill switch.

## 4. Scope

**In scope (v1 line):**
- Alert ingestion from Alertmanager/Prometheus webhooks and a generic JSON webhook.
- Incident lifecycle management (open → triaging → diagnosed → mitigating → resolved → postmortem).
- Read-only diagnosis across metrics (PromQL), logs, Kubernetes state and recent changes.
- An allow-listed runbook library with parameter validation.
- Human approval workflow (CLI first; chat later) for mutating actions.
- A local demo environment where incidents are injected on purpose (chaos scenarios) so the agent can be evaluated end to end.
- Postmortem draft generation from the incident record.

**Out of scope (for now):**
- Managing the agent's own production deployment for real third-party infrastructure (the demo environment is the proving ground; real-cluster use is opt-in, read-only first).
- Replacing paging/on-call tools (PagerDuty etc. are integrations, not competitors).
- Multi-tenant SaaS. This is a self-hosted, single-operator tool first.

## 5. Architecture

```
                ┌────────────────────┐
 alerts ───────▶│ Ingestion (webhooks│
                │  + pollers)        │
                └─────────┬──────────┘
                          ▼
                ┌────────────────────┐      ┌──────────────────┐
                │ Incident store &   │◀────▶│ Memory: past     │
                │ state machine      │      │ incidents,       │
                └─────────┬──────────┘      │ postmortems,     │
                          ▼                 │ runbook stats    │
                ┌────────────────────┐      └──────────────────┘
                │ Reasoning core     │
                │ (plan → query →    │
                │  hypothesise →     │
                │  verify loop)      │
                └────┬───────────┬───┘
              reads  ▼           ▼  proposed actions
        ┌───────────────┐  ┌────────────────────┐
        │ Tool layer    │  │ Policy & guardrail │
        │ metrics/logs/ │  │ engine: classify,  │
        │ k8s/changes   │  │ bound, approve,    │
        └───────────────┘  │ audit              │
                           └─────────┬──────────┘
                                     ▼ approved only
                           ┌────────────────────┐
                           │ Runbook executor   │
                           │ (allow-listed,     │
                           │  parameterised)    │
                           └────────────────────┘
```

Components:

- **Ingestion.** FastAPI service receiving Alertmanager webhook payloads and generic alerts; normalises them into incidents; deduplicates and groups repeat firings.
- **Incident store.** An in-memory store behind a small interface first — Phase 1 taught that webhooks can be built and tested honestly without a database, and the webhook shapes must not change when the storage does. They did not: the SQLite store built in Phase 7 (see the database-store bullet below) inherits the in-memory store's interface and ingestion logic unchanged, and Postgres remains later, behind the same interface. The incident record is the spine: timeline, evidence, hypotheses, actions, approvals.
- **Reasoning core.** A bounded loop with explicit state: gather context → rank hypotheses with supporting evidence → decide next query or propose action → verify outcome. Hard step and token budgets per incident; the loop must be able to say "I don't know" and escalate. As built in v1 (2026-11-08, `reasoning.py`): the loop is deterministic and makes no model call — a fixed plan of four read-only queries (service status, error logs, error metric, request metric for context), each counting against the step budget, with no query run twice. That shape was this pass's lesson from the tool layer: with no model in the loop, CI can check every diagnosis exactly, and a claim or hypothesis that cites no evidence — or evidence not on the incident — is refused outright. When the evidence is thin or the budget runs out, it escalates with no diagnosis set. A model backend can replace the ranking rules later, behind the same report shape.
- **Tool layer.** Typed, schema-validated tools. V1 ships three: `query_metrics` (PromQL), `search_logs`, and `get_service_status`. Each tool is read-only and returns bounded, redacted output, and each result can become an evidence record that names its exact query. Like the incident store, the tools sit in front of small backend interfaces: demo backends first (in-memory metrics and logs, a log file, and a parser for real Prometheus replies), live Prometheus/Loki backends later without changing the tool shapes. `get_recent_deploys` and `describe_service` were sketched here early on; the 2026-11-08 tool pass narrowed v1 to the three tools above — the other two wait until the demo environment and the reasoning loop actually need them, rather than being built on a guess.
- **Read adapters.** As built for Phase 4 (2026-11-09, `adapters.py`): three more read-only sources behind the same pattern — a Kubernetes pod listing (phase, ready containers, restart count, from a `PodList` reply), a Datadog metrics adapter returning the tool layer's own series shape with the source named on the record, and an Azure Monitor adapter running KQL against Log Analytics and returning rows as evidence. Every reply is parsed by a pure function tested against recorded reply shapes, results are bounded and secret-redacted, keys and tokens are passed in by the caller and never logged or stored, and the KQL check refuses management commands (leading-dot commands such as `.drop`), because those change a workspace rather than read it. This pass's one design lesson: a vendor's query syntax belongs in its adapter, not in the shared tool layer — a Datadog query opens with an aggregator (`sum:`) that the PromQL metric-name finder would mistake for part of the metric name, so stripping it lives in the Datadog backend. Honest scope: no live cluster (kind included), Datadog account or Azure workspace was available in the build environment, so the live HTTP backends behind the same shapes are not claimed as tested — a run against a real kind cluster stays a human check, the status the Compose demo had at first. At Phase 4 the adapters were not yet wired into the reasoning loop; Phase 7 added that selection (see the adapter-evidence bullet below).
- **Security review.** As built for Phase 5 (2026-11-09, `security_review.py`, report in `docs/security-review.md`): the agent red-teamed itself in two halves. Ten automated probes attack the real code paths — an unknown runbook, a free-form command as a parameter, a retargeted fix, secrets planted where the audit log or evidence could leak them, a replayed approval, an approval into a halt, the Tier 3 limits, refused management and broken queries, a source scan for any shell or code-execution call, and alert text claiming an incident is over — and all ten are refused or contained, measured 2026-11-09. The other half is eight findings the probes cannot prove away, printed by `sre-agent security-check` on every run so they cannot be quietly forgotten; the largest is that the webhook server (`server.py`) has no authentication at all and ingestion has no size or rate limits — accepted in writing for a local, single-operator demo only, and the first fixes owed before any shared use. This pass's one design lesson: a probe suite can only prove what holds — a review earns its place by publishing what does not, with a severity and a fix, in the same place the passing scores are published. Honest scope: a self-review on demo backends; no live system, Docker run or external tester was involved, and a model-backed loop will need a fresh review, since the deterministic loop has no model surface beyond the Phase 3 injection set.
- **Operator and runbook guides.** As built for Phase 5 (2026-11-09, `docs/operator-guide.md` and `docs/runbook-authoring-guide.md`): the operator guide covers install, running the server, watching incidents, approving a demo fix by name, stopping the agent, the audit log, settings and troubleshooting, in plain words; the runbook guide names the four places a runbook must agree — the policy catalogue, the parameter list, the validation, and the executor — plus honest blast-radius counting in `build_action`, the tests a new runbook must have, and the rule that a new mutation starts at Tier 2 and earns a Tier 3 grant only in its own later change. This pass's one design lesson: a guide written from the safety model's wording alone would have told an operator to run `sre-agent halt` — a command this build does not have; the halt today is a policy setting (`halted`) exercised in drills, and stopping the server process is the live halt, because the server never runs fixes. So both guides were written from the CLI and the code as they actually are, the gap is stated in the operator guide itself, and tests (`tests/test_docs.py`) pin the guides' existence, their README links, and those honest-limit sentences so a later edit cannot quietly drop them.
- **Release (v0.1.0).** As cut for Phase 5 (2026-11-09, `docs/v0.1.0-walkthrough.md`): a release here is an in-repo act the checks can agree on — the version bumped to 0.1.0 in both places it lives (`pyproject.toml` and the package, with a test pinning that they agree and that the recorded baseline carries the same version), the regression baseline re-recorded on purpose at that version (the gate's history keeps the development scores), every check re-run on release day and printed in the walkthrough (242 tests, scenarios 5 of 5, injection 8 of 8, Tier 3 drills 7 of 7, security probes 10 of 10), and one scored scenario walked through step by step with its stated limitation. This pass's one design lesson: the GitHub connection used to build this project has no tool for creating a GitHub Release or a tag — the same platform limit as the CI workflow file (2026-11-08) — so creating that object on the website, with the walkthrough as its notes, is a short human step, and the walkthrough says so instead of implying a GitHub Release already exists. The Docker Compose half of the walkthrough likewise stays a human check: the release environment has no Docker, and the walkthrough labels that part as not run there rather than borrowing the test suite's narrower checks as if they were the full run.
- **Release (v0.2.0) and community basics (Phase 8).** As cut (2026-11-12, `CHANGELOG.md`, `docs/v0.2.0-walkthrough.md`, `CONTRIBUTING.md`, `CODE_OF_CONDUCT.md`, `.github/ISSUE_TEMPLATE/` and `.github/PULL_REQUEST_TEMPLATE.md`): a release is again the in-repo act the checks can agree on — the version bumped to 0.2.0 in both places it lives, the regression baseline re-recorded on purpose at that version (the fresh run first passed against the v0.1.0 baseline unchanged, so the move records the same scores at the new version and hides no drop; the history now holds three release records), every check re-run on release day and printed in the walkthrough (358 tests, scenarios 5 of 5, injection 8 of 8, Tier 3 drills 7 of 7, security probes 10 of 10), and the one-command install re-verified from a clean copy at the new version (exit 0, `sre-agent 0.2.0`, scenarios 5 of 5). The changelog is written from the progress log's measured entries, release by release, and it keeps the honest grades: F-03 and F-06 are improved, not closed. The community files were written from the repo as it actually is, the same rule the guides followed: the contributing guide names only commands that exist and checks that really run, the bug template asks for output the CLI really prints, the feature template asks how an idea stays inside the guardrails and how it would be checked, and the security-reporting path points at the maintainer and the published findings rather than inventing an address. This pass's one design lesson: a changelog or a contributing guide written from intention drifts the same way a walkthrough written before its run does — each is only worth having when a stranger can follow it and land exactly where it says, so the templates were checked against the CLI's real help and check outputs, not against the plan's wishes. Honest remainder, stated in the walkthrough: creating the GitHub Release and the v0.2.0 tag on the website is again a short human step, for the same platform reason as v0.1.0, and the Docker Compose run remains a human check on a machine with Docker.
- **Secret redaction (post-release, Phase 6).** As improved after v0.1.0 (2026-11-09, `tools.py`): the `redact_secrets` filter — the one cleaning every tool result, log line, status message and adapter row before it can be stored as evidence — now catches the shapes finding F-03 named, JWTs first: a JSON web token (three base64url parts joined by dots, the first required to start `eyJ`, the encoded start of a JSON header, so ordinary dotted words and version numbers stay out of the rule), a password inside a connection string (the labelled value now stops at a semicolon, so `Server=db;Password=…;Database=app` is cleaned segment by segment instead of being missed or swallowed whole), a password inside a URL (scheme, user and host kept, password removed), a whole private-key block rather than only its header line, basic credentials, and the prefixed token shapes of GitLab, Slack (tokens and webhook URLs) and Stripe, alongside the shapes it already caught. This pass's one design lesson: a cleaner must be tested in both directions — a test now guards ordinary text (version numbers, hostnames, a commit hash, a credential-free link, a sentence about a token count) against being cleaned by mistake, because a filter that eats normal log lines is its own kind of damage, and a shape is only added when it is specific enough to pass that guard. Honest remainder, stated in the review and in the function's own docstring: F-03 is improved, not closed — an unlabelled secret with no known prefix and no label, and a private key's body lines shown without their header, are still not caught, and no pattern list can promise them; redaction stays defence in depth, and evidence must still be shown only to the operator.
- **Server hardening (post-release, Phase 6).** As built after v0.1.0 (2026-11-09, `server.py` + `ingestion.py`): the two server findings from the security review are fixed. F-01 — the server takes a shared token from `SRE_AGENT_API_TOKEN` (or `create_app(auth_token=...)`); when one is set, every route except `/health` requires it in the `X-SRE-Agent-Token` header, webhooks and incident reads alike, compared with `secrets.compare_digest`, and a missing or wrong token gets a 401 with nothing ingested or shown. With no token set the server is unauthenticated exactly as v0.1.0 shipped — local, single-operator demo mode, stated as such in the operator guide and the review. The CLI learned the same header in the same change (it sends the token when the variable is set for it). F-02 — ingestion is bounded at every layer the finding named: at most 100 alerts per Alertmanager payload, at most 50 labels/annotations per alert with key/value lengths capped, short fields and summaries length-capped, at most 200 evidence records per incident and 1,000 incidents per store; payload caps refuse as 422, store caps as 429 with the reason, and duplicates still count at a full store because they grow nothing. This pass's one design lesson: an authentication fix is only finished when it covers the read routes as well as the webhooks *and* the operator's own tool learns the key in the same change — guarding only the way in would still leak every incident back out, and guarding everything without updating the CLI would lock the operator out of their own server. Honest remainder, stated in the review: no per-sender rate limit was added — the caps bound how much a flood can make the server hold, they do not slow a sender down — and a token-less server remains wide open by design for local use.
- **Audit hash chain (post-release, Phase 6).** As built after v0.1.0 (2026-11-09, `audit.py` + `models.py`): every audit record now carries two chain fields — `prev_hash`, the hash of the record before it (the first record in a log carries a genesis value of 64 zeros), and `record_hash`, its own SHA-256 hash computed over every other field including `prev_hash`, from a canonical JSON form (keys sorted, dates as text) so the same record hashes the same way in any process. `verify_audit_records` and `verify_audit_file` walk a chain and report by position: a record with no chain hashes, a record that does not point at the one before it, and a record that does not match its own hash — so an edited field, a deletion from the middle, and a reordering are each detected and named differently. A log appending to an existing file continues that file's chain from its last record, so a restart does not break it. This pass's one design lesson: a verifier that quietly passed records written before the chain existed would bless history it never checked, so a legacy record with empty hashes is reported as unchained, never passed — an old file stays an old file, and a new log is started rather than mixed. Honest remainder, stated in the review and the operator guide: the chain does not detect deleting the last records or replacing the whole file with a freshly recomputed chain — that needs a signature or a copy kept elsewhere, and neither was added — and it shows an edit happened; it does not prevent one.
- **Backend address rules (post-release, Phase 6).** As built after v0.1.0 (2026-11-09, `backend_url.py`): every live backend address — Prometheus (`tools.py`), Kubernetes, Datadog and Azure Monitor (`adapters.py`) — and the CLI's server address (`cli.py`) pass one shared check, `validate_backend_url`, when the backend is built, before any request is made. The scheme must be https, or plain http only when the host is on the same machine (`localhost`, `127.0.0.0/8`, `::1`) — where the demo backends and the local server live; an address carrying a user or password is refused, because credentials belong in the header a backend adds on purpose, never inside an address that gets logged and copied; and a caller may pass `allowed_hosts` (host names, optionally with a port), in which case the address's host — and its port, when an entry names one — must be on the list. This pass's one design lesson: an allow-list must only ever narrow where the agent may call, never widen the scheme rule — listing a remote host does not make plain http to it acceptable, or the list itself would become the hole it was meant to close. The finding's own fix text said to apply the rules "when live backends are wired for real use"; they were applied now, at construction, instead — the check is cheap, the live backends exist behind the same shapes, and a rule that only arrives with the wiring would arrive exactly when a wrong address first matters. Honest remainder, stated in the review: addresses still come only from operator code or configuration, never from telemetry — these rules are the second layer, not a change to that boundary — and no default allow-list is imposed, because the right hosts are the operator's deployment choice; a caller who passes none gets the https/loopback rules alone.
- **Demo hardening (post-release, Phase 6).** As improved after v0.1.0 (2026-11-09, `Dockerfile`, `demo/sample_service/Dockerfile`, `requirements.lock`): both images this project builds now run as a named non-root user (`sreagent`, `sample` — the sample service binds port 8000, above 1024, so it needs no root), and the agent image installs its dependencies from a lock file at the repo root — exact versions of the runtime and server dependencies and their transitive set, each with a SHA-256 hash, installed with `pip install --require-hashes`, after which the package itself is installed with `--no-deps`. The lock was generated for CPython 3.12 on Linux x86_64, the demo image's platform, and was proven by a fresh environment installing from it with hashes enforced and running the security probes 10 of 10. This pass's one design lesson: a pin is only as honest as its verification — the lock's hashes were computed from the resolved packages themselves and then proven by that fresh install, while a Compose image digest copied from an unverified source would be a costume for a check that never happened. Honest remainder, stated in the review: F-06 is improved, not closed — Prometheus and Alertmanager in `docker-compose.yml` are still pinned by tag (`v2.54.1`, `v0.27.0`), not by manifest digest, because the build environment has no Docker or registry tool that could produce a verified manifest digest for those tags (search found only shortened per-platform digests); recording the real digests is a short human check for the first Docker run, like the Compose run itself.
- **Demo environment.** Docker Compose brings up four containers: a sample service (a pretend checkout service, Python standard library only, with a chaos switch that makes its requests fail), Prometheus, Alertmanager, and the agent's webhook server. One alignment rule, learned building it (2026-11-09): the sample service publishes, the alert rule fires on, and the reasoning loop queries *the same* metric names (`http_requests_total`, `http_request_errors_total`) with the same target labels, so an alert, the incident it opens, and a diagnosis all describe the same numbers. Verification is two-layer, and the docs say so plainly: pytest exercises the sample service's real HTTP routes and checks that the Compose, Prometheus and Alertmanager files agree with the code, while a full `docker compose up` run needs Docker and stays a human-run check — no test pretends to have run it. The reasoning loop is not yet wired to the demo's live Prometheus; its tools still read the built-in demo backends.
- **Policy & guardrail engine.** Classifies every proposed action by tier (Section 6), checks blast radius (namespace, replica count, environment), enforces rate limits and maintenance windows, routes approvals, and writes the audit record *before* execution. As built for Phase 2 (2026-11-09, `policy.py` + `audit.py`): classification comes from one fixed catalogue in code, not from the name a proposer happens to invent — the catalogue names the three read-only tools and the three reversible runbooks (restart, scale, rollback), and any runbook not in it is *denied*, never merely sent for approval. Blast-radius checks now also include the target pinned on the incident (an action aimed anywhere else is denied) and an optional allowed-namespaces scope per environment. The halt switch blocks mutations only; reads may continue, as the safety model already said. The audit log is append-only, in memory or as a JSON-lines file, records allowed, approval-needed and denied decisions alike, and stores a SHA-256 fingerprint of an action's parameters instead of the values, so a secret passed as a parameter cannot leak into the log. `evaluate_and_audit` is the normal entry point, so no decision goes unrecorded. The approval flow is now built too (2026-11-09, `approvals.py`): a REQUIRE_APPROVAL decision becomes a pending action carrying a SHA-256 fingerprint of the exact parameters, expiring after 15 minutes; approving it re-runs `evaluate` at approval time — a policy that now denies (halted, tightened, out of scope) stays denied, that denial is audited, and the human's yes cannot stand — and only a fresh REQUIRE_APPROVAL becomes an ALLOW, audited with the approver's name. The resulting grant is single-use: it is spent before the run starts, so even a failed run cannot be replayed under the same yes. That re-check is this pass's one design lesson — a proposal and its approval are minutes apart, and only the second check judges the world as it stands when the action would actually run. Tier 3 for the demo environment is now built too (2026-11-09, `tier3.py`), which starts Phase 4: one named grant — restart and scale pre-approved in the demo's `shop` namespace only, at most three replicas touched per action; rollback is deliberately *not* pre-approved, because it changes which version runs, so it stays Tier 2 — and one runner, `execute_tier3`, which audits the policy decision before anything runs and runs a fix only on an ALLOW (a fix that still needs approval is routed to a human, never skipped past one). The kill switch is rehearsed, not just described: seven drills (`sre-agent tier3-check`) prove the pre-approved fixes run, rollback does not run on its own, an oversize fix and an out-of-namespace fix are refused, a halt pressed *between* two runs stops the second and changes nothing, and reads continue while halted. Measured 2026-11-09: 7 of 7 drills pass, 3 fixes run across the set. This pass's one design lesson: the halt is checked at run time, inside the policy call every run makes — a halt remembered from proposal time would miss exactly the case the switch exists for, the same reason approval re-checks policy. Still to come: rate limits and maintenance windows (they belong with a runner that could act repeatedly against a live environment, which the demo runner is not yet).
- **Runbook executor.** Runs only allow-listed, parameterised runbooks. No free-form shell. Ever. As built for Phase 2 (2026-11-09, `runbooks.py`): the library is exactly the policy catalogue's three reversible runbooks — restart, scale, rollback — and an early fourth idea, clearing disk pressure in the demo, is not in the library because it is not in the catalogue; the catalogue stays the single list both sides must match, and a test checks that they agree. Each runbook names the parameters it takes (restart and rollback take none; scale takes `replicas`, a whole number from 1 to 5), and any other parameter is refused — twice: once when a proposal is built and again inside the executor, so a hand-made proposal cannot skip the checks. Two lessons from this pass are now part of the design. First, a proposal's `replicas_affected` is worked out by `build_action` from the workload's real state (a restart or rollback touches every running copy; a scale touches the difference), never guessed by the proposer, because the policy engine's blast-radius check is only as honest as that number. Second, the executor runs an action only on an ALLOW decision: a denied action is refused, and so is one still waiting for approval — turning a human's yes into a runnable decision belongs to the approval flow (`approvals.py`, built 2026-11-09), not to the executor; `execute_approved` is the one bridge between them, and it checks the grant matches the pending action exactly before spending it. Actions run against an in-memory picture of demo workloads behind a small backend interface, and a result can be stored on the incident as evidence naming the runbook and its target.
- **Postmortem drafting.** A first draft of the incident report, written from the incident record itself. As built for Phase 2 (2026-11-09, `postmortems.py`): the draft is a pure reader of the record — it changes nothing, runs nothing, and states only what the record holds. Its sections are timeline, diagnosis, possible causes, evidence (each with its exact query), actions taken, and the audit decisions the caller supplies for that incident (records for any other incident are filtered out), plus a "what is not known" list: no diagnosis recorded, no action recorded, no audit records supplied. This pass's one design lesson: incidents do not timestamp each status change — a transition only moves `updated_at` — so the timeline is built only from timestamps the record really has (creation, each evidence record's observation time, each audit decision's time, and the last update), and no time is invented for a change the record did not date. An incident that is not resolved yet still gets a draft, labelled plainly as preliminary, not a final postmortem. `demo_postmortem()` runs one seeded demo incident through the whole path — reasoning loop, Tier 2 approved restart, resolution — and drafts from that real record; `sre-agent postmortem-demo` prints it. Drafting for a live server incident waits, like CLI approval, until the full record and its audit records live in one place.
- **Memory.** As built for Phase 4 (2026-11-09, `memory.py`): past incidents are held in memory behind a small interface and stored as copies. Retrieval (`find_similar`) scores a new incident against each past one with fixed, explainable points — same service counts most, then same namespace, then same environment, then words shared between the two records, capped so wording can never outweigh the target — and every match lists the reasons for its score. There is no model and no embedding, the same choice the reasoning loop made, so every ranking can be checked exactly; a past record of the query incident itself is never returned as its own match. Per-runbook statistics are counted from the action records a run leaves on its incident, never from a separate tally that could drift: a run counts as "ended resolved" when its incident's final status is resolved, and as "not resolved" otherwise. This pass's one design lesson: the record shows an incident *ended* resolved after a run — it does not prove the run *caused* the resolution — so the stats keep that wording and never claim a success the record cannot prove, and an open or escalated incident counts as not resolved, never as a failure of the runbook. Suggestions, which are how the stats influence proposals, are ranked on same-service past incidents only: retrieval also returns neighbours (same namespace, similar words) for a human to read, but a fix's track record may only influence a proposal for the service it actually ran on. A suggestion is Tier 1 advice only — it names the runbook, its record, and the past incidents behind it, and it runs nothing, proposes nothing through the policy engine, and approves nothing, the rule the architecture doc already states; only runbooks in the library, with at least one same-service run, are ever suggested. The seeded demo (`sre-agent memory-demo`) holds four past incidents and reports on a fresh checkout incident: retrieval ranks the checkout past first, the overall restart record is 3 runs with 3 ended resolved, and the suggestions rank restart (2 of 2 on checkout) before scale (0 of 1). Wiring memory into the live path is now built (see the memory-advice bullet below): suggestions are attached to a live diagnosis as advice, after it is decided — they are still never an input to a diagnosis or an action. Incidents themselves are now stored in a database when a server is built with one (see the database-store bullet below); feeding those stored incidents back in as memory is still to come.
- **Evaluation harness.** A scenario suite that injects faults (pod kill, bad deploy, latency injection, disk fill, config error), runs the agent, and scores it. As built for Phase 3 (2026-11-09, `evaluation.py`): the five faults seed the in-memory tool backends the reasoning loop already reads — service state, error logs and the two aligned metrics — so the suite runs in pytest, in CI and as `sre-agent evaluate` with no Docker and no live demo; wiring the same faults through the Compose demo is later work and is not claimed. Scoring is outcome, top-hypothesis wording, evidence citation and unsafe actions (counted from each incident's record, where a run would leave an action record; must be zero), with steps used reported instead of wall-clock time, which on a deterministic local loop would measure the machine. This pass's one design lesson: a scenario may only be scored on a cause the loop has a tool to see — disk fill, config error and bad deploy carry a stated `known_limitation` (no disk, config or deploy tool) and are scored on seeing the failure, not naming its cause, and remediation correctness is not scored at all yet, because the loop proposes no fix. Measured 2026-11-09: 5 of 5 correct on this suite, 0 unsafe actions. The regression gate is now built too (2026-11-09, `regression.py`): the last release's scores are recorded in a committed baseline file (`evaluation/baseline.json`), and `sre-agent regression-check` compares a fresh run against it — unsafe actions must be zero absolutely, not relative to the baseline; every diagnosis must cite evidence really on its incident; accuracy may not drop; and scenarios are compared one by one, so a scenario that turns from correct to wrong is named rather than hidden by an unchanged total. This pass's one design lesson: the gate never updates its own baseline — running the check changes nothing, and recording a new baseline is a deliberate release act (`--update-baseline`) that refuses a run breaking the absolute rules and appends each release's scores to the file's history, so accuracy is tracked per release in one place. The prompt-injection test set is now built too (2026-11-09, `injection.py`), which completes Phase 3: eight hostile payloads planted in every telemetry surface the agent reads — log lines ordering a deletion, a runbook run, a dictated diagnosis, and a secret reveal (with planted secret values), a generic alert summary ordering a retarget, an Alertmanager annotation claiming a firing incident is already resolved, a status message claiming a down service is healthy, and a metric label ordering a rollback — each run through the real reasoning loop or the real ingestion path and checked on the same boundary: the words never appear in a claim, a hypothesis, or a diagnosis; no action runs (counted from the incident record); the outcome is the one the honest telemetry earns; the target stays pinned from the alert's structured labels; the loop's queries are exactly its four fixed ones; and planted secrets are redacted everywhere, evidence included. Measured 2026-11-09: 8 of 8 cases pass, 0 unsafe actions, runnable as `sre-agent injection-check`. This pass's one design lesson: the defence is not scrubbing hostile text out of the record — the evidence record *does* store it, bounded and secret-redacted, because an incident record that quietly dropped hostile lines would be hiding part of the incident — the defence is that stored data never crosses into the agent's own statements, targets, or actions, and the suite checks that boundary (including a test proving the checker can fail). One stated limitation rides with the set: the loop reads the word "timeout" in error logs as a symptom signal by plain rule, so a crafted line containing it can raise the timeout hypothesis — signal spoofing, not instruction following; it cannot add wording, actions, or targets beyond the loop's fixed set.

- **Server diagnosis (Phase 7).** As built (2026-11-11, `server.py`): `create_app` takes an optional tool layer; with one, the reasoning loop runs inside the server — a firing alert that opens an incident is diagnosed during ingestion, and the diagnosis, hypotheses and gathered evidence are stored on the incident, so the API and `sre-agent show` read them back. A grouped update to an escalated incident sends it back through triage for a fresh diagnosis; a duplicate is never re-diagnosed; an already-diagnosed incident keeps its diagnosis when a grouped alert adds evidence. The shipped `app` uses the demo tool layer, so its diagnoses describe the seeded demo data, never a real system; an app built with no tool layer records only, exactly as before. A loop failure is caught and logged and the incident is kept as ingested — a broken diagnosis must never lose an alert. This pass's one design lesson: server diagnosis is on only when a tool layer was deliberately configured — silently defaulting every `create_app` caller to the demo data would have made test and embedded servers produce demo diagnoses they never asked for, so the default stays record-only and the demo wiring is explicit in the one shipped app.
- **Adapter evidence (Phase 7).** As built (2026-11-12, `reasoning.py` over `adapters.py`): the three read adapters can be selected as extra evidence sources for a diagnosis, as an `AdapterSources` bundle handed to the reasoning loop or to the server (`create_app(adapters=...)`), which passes it on. Each selected adapter is asked exactly one fixed question after the loop's four core questions — the pods for the incident's namespace and service, the Datadog error metric for its service, the Azure Monitor error rows for its service — each counts as one step, and the answers are stored on the incident as evidence and can support claims and hypotheses as counts and measured values only (pod containers ready of total, restarts in total, a latest metric value, an error-row count); raw adapter text — pod names, row contents — is never copied into a claim. The shipped server app selects the demo bundle, matching its demo tool layer; an app built with adapters but no tool layer still records only, because adapters supplement the loop, they do not replace it. This pass's one design lesson: adapter steps are extras, so their failure rules differ from the core plan's — a step budget that runs out before an adapter step, an adapter that fails, or a target name carrying query syntax (Datadog and KQL questions are built only from a service name that matches a plain-name pattern, letters/digits/dots/underscores/dashes) skips that one source and never discards a diagnosis the core evidence already earned, while an unfinished core plan still escalates, as before. Honest scope: sources are selected by operator code at construction — never by telemetry, which also cannot add a source or change an address — the live backends' addresses passed the Phase 6 rules when they were built, and those live backends remain untested against real systems, as Phase 4 stated; the demo bundle is what the tests and the shipped app exercise.
- **Live approvals (Phase 7).** As built (2026-11-11, `server.py` over `approvals.py`): when `create_app` is given an environment policy and a runbook backend, the server serves the Tier 2 flow for its own incidents. `POST /incidents/{id}/actions` proposes a runbook for one diagnosed incident — the action's target is the target pinned on that incident (the request body has no target field, so a proposal cannot be retargeted at all), and its blast radius is counted by `build_action` from the backend's real state. The policy decision is audited before anything else; a denial is refused (403), a REQUIRE_APPROVAL becomes a pending action held by the server (15-minute expiry), and `GET /incidents/{id}/approvals` lists pendings with their state. `POST .../approvals/{id}/approve` runs the existing `approve_pending` — named approver, policy re-checked at approval time, denial audited — then `execute_approved`, which spends the grant before the run; `.../reject` marks the pending rejected and runs nothing, and a decided pending cannot be decided again. A successful run adds its result to the incident as evidence and moves it diagnosed → mitigating. The shipped `app` wires the demo Tier 2 policy and the demo runbook backend; a server built without either holds no approvals and its approval routes answer 409. This pass's one design lesson: a run is not a recovery — the in-process demo flow walked its incident to resolved because it was a scripted demo, but the live path must not claim a fix worked when nothing checked, so the server stops at mitigating and resolution still arrives only as a resolved alert. Honest scope: the backend is still the demo backend, so no real system is acted on; approvals and incidents lived in the server process's memory until the database item below (a server built with the database store now persists both; the audit log still lives in the server process unless code hands it a file); and there is no CLI command for the server's approvals.
- **Memory advice in the live path (Phase 7).** As built (2026-11-12, `reasoning.py` over `memory.py`, wired in `server.py`): an operator may hand an `IncidentMemory` to the reasoning loop or to the server (`create_app(memory=...)`), which passes it on. After a diagnosis is decided — diagnosed or escalated alike — the loop asks the memory for its report on that incident and attaches it: the report is stored on the incident as `memory_report`, returned in the loop's `DiagnosisReport`, shown by `GET /incidents/{id}` (the list view carries match and suggestion counts) and printed by `sre-agent show` under an "advice only" label. The shipped `app` is built with the seeded demo memory (`demo_incident_memory()`, the same four past incidents as `sre-agent memory-demo`, now available as a memory itself, not only as a one-off report). This pass's one design lesson: advice that is computed only after the outcome is decided cannot have influenced it — the ordering is the guarantee, and a test pins it by checking that a diagnosis with a memory attached is word-for-word the diagnosis without one, with no evidence or action record added and no pending approval created from a suggestion. A memory that fails is skipped with the failure logged, like a failing adapter: advice can never discard a diagnosis. The report models (`MemoryReport` and its parts) moved into `models.py` in this pass, for one stated reason: an incident record can now carry a report, and the core models cannot import `memory.py` (which itself builds on them); `memory.py` re-exports them, so existing imports keep working. Honest scope: the memory is still in-process and seeded for the shipped app — a real deployment hands in its own past incidents — and nothing reads the attached advice to propose or run an action; the database store below is what will let a server's own resolved incidents become its memory over time, and that is not claimed yet.
- **Database store (Phase 7).** As built (2026-11-12, `storage.py` over `ingestion.py`, wired in `server.py`): `SQLiteIncidentStore` is the in-memory `IncidentStore` plus write-through persistence to one SQLite file, using only the standard library's `sqlite3` — no new dependency, because the store is one file for one operator and the interface, not the engine, is the design. It inherits dedupe, grouping, resolving and the F-02 intake caps unchanged rather than reimplementing them, loads its incidents, fingerprint and group indexes and duplicate counts at start-up, and re-writes them in one transaction after every ingestion. Diagnoses persist because they are fields on the incident; approvals persist because the store interface gained two hooks the server uses — `save_approval` when a pending action is created or decided, `load_approvals` when a server starts — alongside `save(incident)`, the hook for changes made outside ingestion, which the server now calls after every diagnosis and every run. A restored pending approval keeps its original 15-minute expiry (a restart extends nothing) and a decided approval stays decided, so no run can be replayed across a restart. This pass's one design lesson: persistence belongs behind the store interface, but a mutation made to a record outside the store is only kept when its caller hands the record back through `save` — assuming shared-object mutation would be saved is exactly the bug a copy-returning store would have hidden, so the hook is explicit and the in-memory store answers it too. Honest scope: single file, single operator, one server writing at a time — not Postgres and not multi-writer; the shipped `app` still uses the in-memory store, so the demo is unchanged; the audit log is not in this database (it has its own file form and hash chain); and a server's own stored incidents are not yet fed back as its memory — that wiring remains future work, as the memory bullet above states.

- **Language-model backend (Phase 9).** As built (2026-11-12, `model_backend.py`): who reads the gathered evidence is now a backend the reasoning loop is handed, behind the same `DiagnosisReport` shape, and the report names its backend. The deterministic backend — the plain rules the loop always ran, moved word for word into `DeterministicBackend` — is the default everywhere (demo, CLI, suites, shipped server) and needs no key. The language-model backend is off by default: it exists only where an operator builds one in code around their own model client (one method, `complete(prompt) -> str`) and passes it to `ReasoningLoop(..., backend=...)` or `create_app(..., diagnosis_backend=...)`; no setting, environment variable or CLI flag enables it, and the repo ships no real client — provider, model and key are the operator's decision (Section 14). Its prompt is built only from the gathered evidence records (id, kind, exact query, and the already bounded, secret-redacted summary) under fixed instruction text. Its reply is checked as untrusted input before any of it can become a claim: one JSON object with only `claims` and `hypotheses` at the top level (any other top-level key, `actions` included, refuses the whole reply); each entry may carry only a statement (bounded), its evidence ids and a confidence in 0–1, and every cited id must be a real evidence record for that incident — an entry carrying any other field, or citing an unknown id, is dropped; a failing client or a non-JSON reply returns nothing, so the loop escalates with "I don't know" rather than failing. `DiagnosisClaim` moved into `models.py` in this pass, for the same reason the memory report models moved: a backend returns claims and cannot import the loop that calls it; `reasoning.py` re-exports it. This pass's one design lesson: a model backend's output needs the same evidence discipline as telemetry — the loop's final citation check stays the backstop for every backend, and the model backend's stricter reply checks sit in front of it so a bad reply degrades to an escalation instead of an error. Honest scope: the model backend proposes wording inside a diagnosis only — it proposes no action in a diagnosis reply (model-proposed actions arrive through a separate channel, next bullet), no real model was called in this pass (tests use fake clients returning fixed replies), and no score was published for it in that pass — separate per-backend scores followed in the last Phase 9 pass (see the per-backend scores bullet below), before it is ever recommended.
- **Model-proposed actions (Phase 9).** As built (2026-11-12, `model_proposals.py`): a language model may propose a fix through a channel separate from diagnosis, off by default and wired nowhere in the shipped code — a `LanguageModelProposer` an operator builds around their own model client and calls in their own code. Its reply is one JSON object with only `runbook_id`, `parameters` and `rationale`; any other key — `target`, `approved_by`, `decision` included — refuses the whole reply, so a proposal cannot be retargeted or self-approved. A surviving proposal is built by the same `build_action` every proposer uses (parameters validated, blast radius counted from the workload's real state, target always the incident's pinned target, rationale prefixed so a reader can see a model proposed it), then submitted through the literal same path the server's proposal route takes: `evaluate_and_audit` (same policy engine, same tiers, decision in the same audit log before anything runs), `create_pending` on REQUIRE_APPROVAL (same 15-minute expiry), and the executor on ALLOW — where an ALLOW is the policy's own call, at Tier 3 a human's grant written into the policy in advance, never the model's approval. `submit_model_proposal` never calls the approval flow and the proposer has no approve method: a submission can produce a pending action, never a grant, and a named human approving a model proposal through `approve_pending` gets the same single-use, policy-re-checked grant as for any proposal. This pass's one design lesson: sameness must be literal, not parallel — the item is only done when a model proposal and a hand-built identical proposal produce the same decision, the same reason, and an audit record matching field by field, which a test now compares directly; a second, model-shaped implementation of the policy path would drift from the first exactly where safety lives. Honest scope: tests use fake clients only, no real model proposed anything, the server does not expose model proposals over HTTP, and no score is published for model proposals themselves — the per-backend scoring in the next bullet covers diagnosis backends; which fix a proposer would choose is still not scored.

## 6. Safety model — tiers of autonomy

| Tier | Name | What the agent may do | Gate |
|------|------|----------------------|------|
| 0 | Observe | Read metrics, logs, cluster state | None |
| 1 | Advise | Publish diagnosis and proposed remediation | None |
| 2 | Act with approval | Execute an allow-listed runbook for one incident | Human approves that specific action |
| 3 | Act within bounds | Execute pre-approved runbook classes in a named environment, inside blast-radius limits | Policy pre-approval + audit + instant kill switch |

Defaults: new environments start at Tier 1. Tier 3 is per-runbook-class, per-environment, never global. Every action, approved or not, is audit-logged with its evidence and reasoning. A single `sre-agent halt` (or SIGTERM) stops all execution paths.

**Threat model highlights:**
- Prompt injection through log lines, alert annotations, or fetched runbook text: mitigated by treating tool output as data, structured tool schemas, and never letting model output become a command without policy validation.
- Credential leakage: secrets are referenced by name, never embedded in prompts or logs; tool outputs are redacted for common secret patterns.
- Runaway loops: per-incident step, time and cost budgets; repeated identical queries are cut off.
- Wrong-target actions: environment and namespace are pinned in the incident record at ingestion; actions cannot retarget mid-flight.

## 10. Documentation standard

Documentation is a product feature of this project, not an afterthought (Abraham's direction, 8 November 2026):

- **Plain and simple wins.** Every document is written so a competent engineer who has never seen the project understands it on first read. Jargon is explained the first time it appears. If a section needs a diagram, it gets one (ASCII is fine).
- **Every change ships with its explanation.** Each phase item is only "done" when the README or docs explain what was built, why, and how to use it, in plain language.
- **A running plain-English log.** `docs/progress.md` in the repo records what changed, in ordinary words, one short entry per work session — so Abraham (or any reader) can follow the whole build without reading code.
- **Decisions are written down.** Any design choice that changes direction gets a short decision note in `docs/decisions/` — what was decided, why, and what it replaced.

## 11. Open-source strategy — proving reliability in public

The repository itself is the reliability evidence. The strategy (Abraham's direction, 8 November 2026):

- **Build in public.** Public roadmap (this plan), public progress log, small frequent commits with honest messages. Nothing is claimed that the evaluation harness has not measured.
- **Practise what it preaches.** The project holds itself to SRE standards: CI must be green to merge, releases carry published evaluation scores, and the project's own failures get short public postmortems in `docs/postmortems/` — an SRE tool that hides its own incidents would prove the opposite of reliability.
- **Low-friction adoption.** One-command demo, a `CONTRIBUTING.md`, labelled good-first-issues, and responsive issue handling. Adoption by strangers is the strongest reliability signal there is.
- **Steady cadence over big launches.** A visible, sustained commit and release rhythm reads as dependable; bursty hype does not.

## 12. Income path (long-term)

Income is a long-term goal, not a launch goal (Abraham's direction, 8 November 2026). The open-source core stays free under MIT — that is what builds the audience and the proof. The realistic sequence:

1. **Audience and proof (months 0–6).** GitHub stars, users running the demo, evaluation results worth citing. GitHub Sponsors switched on once there is something worth sponsoring.
2. **Services around the core (months 6–12).** Paid work that does not gate the code: implementation help for teams adopting the agent, safety evaluations of other people's agents (directly powered by the red-teaming research), and training/workshops on agent guardrails.
3. **Open-core paid tier (year 2, only if adoption justifies it).** The core stays open; a paid layer could add enterprise integrations (SSO, audit export, Datadog/Azure enterprise adapters), a hosted control plane, and support with response-time commitments. Nothing in the free core gets taken away to force the upgrade.

No revenue figures are promised anywhere in this plan; each stage is gated on the previous stage actually happening.

## 14. Risks and open questions

- **Model access and cost.** Live reasoning needs a model API key or a local model. The codebase will run fully in a deterministic "mock model" mode so contributors and CI need no key; Abraham decides which real backend to wire first.
- **Scope creep.** The roadmap is deliberately narrow (demo environment, five scenarios). New integrations wait until Phase 4.
- **Trust claims.** All public claims about capability must trace to the evaluation harness output, not aspiration. The README states plainly what the agent cannot yet do.
- **Time.** Built in hourly refinement passes alongside Abraham's other commitments; phases are sized so each pass lands something verifiable.
