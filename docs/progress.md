## 9 November 2026 (Phase 6 is complete, with one remainder stated) — the demo runs as nobody special, and its packages are locked

- The last item in Phase 6 is improved: F-06 — the demo containers and the dependencies were not hardened. Two of its three parts are now done, and the third is stated plainly as a remainder rather than faked.
- **Not root any more.** Both images this project builds — the agent's and the pretend checkout service's — now create a named user (`sreagent` for the agent, `sample` for the service) and run as that user. If something inside a container is ever tricked into misbehaving, it no longer holds the container's master key. The sample service can do this easily because it listens on port 8000, and ports above 1024 do not need root.
- **Packages are locked, with fingerprints.** The agent image used to install whatever the newest allowed version was on the day it was built. Now it installs from a new file in the top folder, `requirements.lock`: the exact version of every package the server needs, each with a SHA-256 hash (a long fingerprint of the package's bytes), and the install checks every hash as it goes — a package whose bytes do not match is refused. The package itself is then added with no further downloads. The lock was made by resolving the dependencies for the same kind of machine the demo image runs on, and it was proven before this was written down: a fresh, empty environment installed from the lock with the hash checks switched on, and the project's own security check ran in it, 10 of 10.
- **The remainder, stated plainly.** Prometheus and Alertmanager — the two ready-made images the demo borrows — are still pinned in the Compose file by their version tags (`v2.54.1`, `v0.27.0`), not by image digest. A digest is a fingerprint of the whole image, and pinning by one only means anything if the fingerprint was actually checked against the registry. Where this project is built there is no Docker and no registry tool that could produce a verified digest for those tags, and search turned up only shortened, per-platform digests — not the manifest digest a Compose file needs. Writing down an unverified number would either break the demo or pretend a check happened that did not. So the tags stay, the gap is written here and in the security review, and recording the real digests is a short job for the first person who runs the demo with Docker. Like F-03's secret cleaning before it, F-06 is recorded as **improved, not closed**.
- One design lesson, written into the plan: a pin is only as honest as its verification — a lock file whose hashes were computed from the packages themselves, and then proven by a fresh install, is a real check; a digest copied from an unverified page would be a costume for one.

## 9 November 2026 (Phase 6 continues) — backend addresses are checked before a token can be sent to one

- The next finding in the security review's order is done: F-05 — the live backends (the parts that would talk to a real Prometheus, Kubernetes, Datadog or Azure Monitor) took their address from whoever set them up, with no checks, and sent their login token to that address as a header. A mistyped address — or a hostile one slipped into a config file — would quietly receive a live token, and a plain `http://` address would carry it across a network with no encryption at all.
- Now every one of those addresses, and the command-line tool's own server address, passes one shared check (`validate_backend_url` in the new `backend_url.py`) at the moment the backend is built, before any request is made. The rules, in plain words: the address must use `https://` — the encrypted kind — for anything beyond this machine. Plain `http://` is still allowed to this machine itself (`localhost`, `127.0.0.1` and friends), because that is where the demo backends and the local server live, and nothing crosses a network there. An address that carries a user name or password inside it (`https://user:secret@host`) is refused — passwords belong in the header a backend adds on purpose, never pasted into an address that gets logged and copied around. And whoever sets a backend up may also give it a list of allowed hosts; when they do, the address must be on that list.
- One rule about that list matters most, and a test pins it: **the list can only narrow where the agent may call — it can never widen the rules above.** Naming a far-away host on the list does not make plain `http://` to that host acceptable. A list that could do that would be a hole wearing a safety feature's clothes.
- The command-line tool follows the same rules for its server address, because it can carry your server token: pointing it at a plain-http server on another machine is now refused with a plain reason, before anything is sent. The normal local address, and any `https://` address, work exactly as before.
- The security check grew in the same pass: its query-guards probe now also tries to build backends with a far-away plain-http address, an address off its allow-list, and an address with a password inside it — all refused — and checks that the good addresses are accepted. The review's printed findings now show F-05 as fixed.
- One design note, written into the plan: the finding suggested applying these rules "when the live backends are wired for real use". They were applied now instead, at build time — the check is cheap, and a rule that only arrives with the wiring would arrive exactly when a wrong address first matters. What did *not* change, stated plainly: addresses still come only from the person running the agent, in code or configuration — never from an alert, a log line, or anything the agent reads. These rules are the second layer, for the day that person's address is wrong. And no built-in list of "the right hosts" is imposed: which hosts are right is the operator's choice, so the allow-list is there to use, not forced.

## 9 November 2026 (Phase 6 continues) — the audit log can now prove it was not rewritten

- The next finding in the security review's order is done: F-04 — the audit log file had no tamper protection. The audit log is the written record of every decision the policy engine makes (allowed, needs approval, or refused), and before this pass anyone who could edit its file could change a decision in it and nothing would show.
- Now every record is chained to the one before it, using hashes (long fingerprints that change if even one letter of what they cover changes). Each record carries the hash of the record before it — the first record in a log carries a starter value of 64 zeros — and its own hash, worked out over everything in the record, including that link. So the records form a chain, in order, and a new check (`verify_audit_file` for a file, `verify_audit_records` for a list, both in `audit.py`) walks the chain and reports exactly where it breaks.
- What that catches, in plain words: changing any field of a written record (a refused decision quietly turned into an allowed one is the test case), deleting a record from the middle, and swapping two records around — each is reported by its position in the file, and each is named for what it looks like. A log that appends to a file written earlier picks the chain up where that file left it, so restarting the program does not break it. And a record written before this fix, with no chain hashes on it, is reported as unchained — never quietly passed.
- The honest limits, stated here and in the review, because a chain is not magic: deleting the *last* records leaves nothing behind them to point back, so that is not detected; and replacing the whole file with a brand-new chain, hashes and all recomputed, is not detected either. Catching those would need a signature or a second copy kept somewhere else, and neither was added. What the chain does is make the ordinary edits — the ones an incident review would worry about — show.
- The security check grew in the same pass: its audit-log probe now also checks that the chain verifies exactly as written, and that editing a record breaks it. The review's printed findings now show F-04 as fixed, with the whole-file limit in its summary.
- One design lesson, written into the plan: a chain that cannot tell an old, unchained record from a good one would be worse than none — it would bless history it never checked. So the verifier treats a missing hash as a problem to report, not as a pass.
- Nine new tests pin all of this. All 268 tests pass, including the safety tests, and the style and type checks are clean. The measured gates did not move: scenarios 5 of 5, injection 8 of 8, Tier 3 drills 7 of 7, security probes 10 of 10, and the regression gate passes.

- What it catches now that it did not before, in plain words: **web tokens** (JSON web tokens — the long three-part strings, joined by dots, that services use as login tokens; the rule requires the first part to start with the letters every such token's first part starts with, so normal dotted words and version numbers are not eaten by mistake); **passwords inside connection strings** (the kind that read `Server=db;Password=…;Database=app` — the password part is cleaned and the rest of the string is kept, where before the password could slip through or the whole string could be swallowed); **passwords inside web addresses** (`https://user:password@host` — the address and user stay readable, the password goes); **a whole private key**, not just its first line; **basic login credentials**; and the token shapes used by **GitLab, Slack and Stripe**, alongside the ones it already caught (labelled passwords and tokens, AWS keys, GitHub tokens).

A new test checks that ordinary text comes through untouched — a version number, a hostname, a long commit hash, a link with no password in it, a sentence that merely talks about a token count. A filter that quietly eats normal log lines would be its own kind of damage, so a new shape is only added when it is specific enough to pass that guard.
- The security check itself got stronger in the same pass: its planted-secrets probe now also plants a web token in a log line and a connection-string password in a status message, and checks both are gone while the harmless rest of the string (`Database=app`) survives.

A secret with no label and no known shape — just a random string that only its owner knows is secret — is still not caught, and neither are a private key's middle lines shown without their first line. ## 9 November 2026 (Phase 6 starts) — the server grows a lock, and intake gets limits

- The roadmap was finished at v0.1.0, so this pass starts the work the plan itself named as the first thing owed afterwards: the security review's two server findings, F-01 and F-02. - First, a piece of good bookkeeping: at the start of this pass the public repository was checked and it is fully caught up — the v0.1.0 release batch that was waiting on an approval card has landed (eleven files, the newest commit is the release plan), so the public record and the local copy agree again.
- **F-01, the lock.** The server now takes a shared token — a secret word you choose — set with the environment variable `SRE_AGENT_API_TOKEN`. When a token is set, every page the server serves except the health check requires that exact token in a header (`X-SRE-Agent-Token`): the two webhook doors and the two incident-reading doors alike. A request without it, or with the wrong one, gets a plain "401 — not allowed" and nothing is taken in or shown. The comparison is done in constant time, the careful way, so guessing cannot learn the token from timing. The command-line tool learned the same trick: set the same variable for it and it sends the token on every read, so fixing the server did not lock the operator out of their own tool. Alertmanager can send the header too. The honest limit, stated everywhere the fix is described: **with no token set, the server is still wide open, exactly as the review found it** — that is the local demo mode, and it stays for one operator on their own machine only.
- **F-02, the limits.** Everything that arrives is now measured before it is stored. One Alertmanager message may carry at most 100 alerts. One alert may carry at most 50 labels and 50 annotations, with limits on how long each name and value can be, and the short fields and the summary are length-limited too. One incident may hold at most 200 evidence records, and the store may hold at most 1,000 incidents. Past a limit in the message itself, the request is refused as invalid; past a store limit, the server answers 429 ("too much — slow down") and says which limit it was. A repeat of an alert already counted still counts as a duplicate even when the store is full, because it adds nothing new. One thing was *not* added, and the docs say so: a per-sender speed limit. A flood can now fill the store up to its cap and then gets refusals — what it can no longer do is grow the server's memory without any bound, which was the harm the finding named.
- One design lesson, written into the plan: the lock had to cover the reading doors as well as the webhook doors, and the operator's own tool had to learn the key in the same change — an authentication fix that only guards the way in, or that locks the operator out, is not finished.

## 8 November 2026 (near midnight) — Phase 1 continues: the agent can explain what is wrong, with evidence

- The agent can now do the figuring-out step. Given an incident, it asks a small, fixed set of questions — is the service up, what do its error logs say, are errors showing in the metrics, how much traffic is there — stores every answer on the incident as evidence, and writes a diagnosis report.
- Every sentence the report claims as a fact points at the evidence behind it, and the printed report shows the exact query under each claim, so a reader can re-run that query and check. A claim with no evidence behind it cannot even be built: the data model refuses it, and the loop checks every cited record is really on the incident before writing anything down.
- Possible causes are ranked, and they get stronger when two different sources agree — error logs that mention a timeout *and* an error metric that is not zero make a stronger case than either one alone. Traffic on its own never counts as a diagnosis.
- This first version uses plain rules and no language model. That is deliberate: it runs with no API key, and the tests can check every diagnosis exactly. A model can take over the ranking later, behind the same report shape.
- When the evidence shows no clear problem, the report says "I don't know", no diagnosis is set, and the incident is handed to a human ("escalated") instead of being guessed at. The same happens if the step budget runs out mid-plan: a half-finished plan supports no claims at all.
- Log lines stay data, never orders: claims are built from counts, statuses and measured values, so a crafted log line telling the agent to delete something appears in no claim and changes nothing.
- One honest catch, found by checking before this pass: the public repository was one pass behind — the tool layer from earlier tonight was verified locally but had not landed on GitHub. This pass's upload includes those two files as well, so the public repo now matches the local record.

## 8 November 2026 (late night) — Phase 1 continues: the agent can read evidence

- The agent can now look at a problem, not just hear about it. It has three tools, and all three only look — none of them can change, restart, or delete anything.
- The first tool asks about numbers ("metrics"): it takes a question in PromQL, the query language Prometheus uses, and returns the matching measurements. The second searches log lines — the written record services leave behind — by a word or phrase, a service, or a level like ERROR. The third checks a service itself: is it healthy, degraded, or down, and how many of its copies are ready?
- Every question is checked before it runs. An empty question, a question that is too long, a broken PromQL string, or a request for more results than the fixed limit is refused with a clear reason.
- Every answer is kept small on purpose, and if part of it had to be cut off, the answer says so. Answers are also cleaned: common secret shapes — a password, a token, a key written into a log line — are replaced with "[redacted]" before anything is stored or shown.
- Each answer can become an evidence record for an incident, and the record always names the exact query that produced it. That is what will let the coming diagnosis say "I think this because that query showed that", instead of just sounding sure.

## 8 November 2026 (night) — Phase 1 starts: the agent can receive alerts

- The agent has a front door now. Monitoring tools can send it alerts two ways: the shape Prometheus Alertmanager already sends, and a simple "generic" shape (one alert as a small piece of JSON) for tools that do not speak Alertmanager.
- Each alert becomes an incident — the agent's record of a problem — and the incident goes straight into "triaging", which means the agent has started looking at it. The alert itself is kept on the record as the first piece of evidence.
- Alerts repeat a lot in real life, so two rules keep the record clean. If the exact same alert fires again, it is counted as a copy (a "duplicate") on the same incident instead of opening a new one. If a different alert arrives for the same service with the same alert name, it joins the open incident as extra evidence ("grouping") instead of starting a second file for the same problem.
- When an alert says it has resolved, the incident closes. If the same problem fires again later, it opens a fresh incident, as it should.
- For now the incidents are kept in memory, behind a small, simple store. A database comes later; the way alerts arrive will not change when it does.
- There are also simple ways to look at what the agent knows: a health check, a list of incidents, and the full record for one incident.
- Fourteen new tests cover all of this. All 33 tests pass, including the safety tests, and the style and type checks are clean.
