# v0.2.0 — release notes

Released 12 November 2026. This page is the release record
for v0.2.0: what shipped since v0.1.0, the scores measured on
release day, and the limits that ship with it. The full
change list is in [../CHANGELOG.md](../CHANGELOG.md). For the
step-by-step run through the live path, use the README's
"Walkthrough: one alert, end to end" — it was written from a
real run in the pass that built it, and it is the walkthrough
for this release too.

## What v0.2.0 is

Everything v0.1.0 did, plus the two phases that followed it:

- **Phase 6 — the security findings fixed or improved.**
  The server takes a shared token when one is set (F-01) and
  ingestion is capped at every layer (F-02); secret redaction
  catches more shapes (F-03, improved, not closed); audit
  records are hash-chained and verifiable (F-04); live
  backend addresses are checked — https beyond this machine,
  an optional allow-list (F-05); and the demo images run as
  non-root users and install from a hashed lock file (F-06,
  improved, not closed). The findings are tracked in
  [security-review.md](security-review.md).
- **Phase 7 — the live path wired.** The reasoning loop runs
  inside the server, so a new alert is diagnosed as it
  arrives; approvals for a server's own incidents are served
  by that server over HTTP, under the same single-use,
  15-minute, re-checked rules; the read adapters and the
  incident memory can feed a diagnosis (the memory as advice
  only, attached after the diagnosis is decided); incidents,
  diagnoses and approvals can persist in a SQLite database
  file; and an evaluation gate file checks all five suites
  plus a fully wired server in one place.
- **Phase 8 — polish for users.** `./quickstart.sh` installs
  everything in one command and proves it; the README carries
  a full live-path walkthrough; and this release adds the
  changelog and the community basics — a contributing guide,
  a code of conduct, issue templates and a pull request
  template.

Every number below was printed by the command beside it, run
on 12 November 2026 against this release's code, after the
version was bumped and the baseline re-recorded.

| Full test suite | `pytest` | 358 tests pass, safety suite included |
| Chaos scenarios | `sre-agent evaluate` | 5 of 5 correct, 0 unsafe actions |
| Regression gate | `sre-agent regression-check` | PASS against the v0.2.0 baseline |
| Prompt injection | `sre-agent injection-check` | 8 of 8 cases pass, 0 unsafe actions |
| Tier 3 and kill switch | `sre-agent tier3-check` | 7 of 7 drills pass |
| Security probes | `sre-agent security-check` | 10 of 10 probes pass; findings F-01–F-08 as recorded in the changelog |

For this release the regression baseline was re-recorded on
purpose, the way the gate requires: the package version is
now 0.2.0 in both places it lives (`pyproject.toml` and the
package itself — a test checks they agree, and that the
recorded baseline carries the same version), and
`evaluation/baseline.json` now holds the v0.2.0 scores (5 of
5, 100%, 0 unsafe actions) with the v0.1.0 and development
scores kept in its history. Before the baseline moved, the
fresh run was also checked against the v0.1.0 baseline and
passed it — the new baseline records the same scores at the
new version; it does not hide a drop.

The one-command install was verified from a clean environment
for this release as well: a fresh copy of the repository with
no `.venv` ran `./quickstart.sh` end to end — it printed
`sre-agent 0.2.0`, one demo diagnosis, and scenarios 5 of 5.

One honest note about the release itself: this is an in-repo
release. The GitHub connection used to build this project has
no tool for creating a GitHub Release or a tag, so that step
— like the CI workflow file before it — is a short manual
step on the GitHub website, using this page as the release
notes. Nothing about the code, the scores or the checks above
depends on it.

## Try it

```bash
git clone https://github.com/KakoozaJerry/sre-agent.git
cd sre-agent
./quickstart.sh
```

Then follow the README's "Walkthrough: one alert, end to
end": start the shipped server, send the demo checkout
alert, read the diagnosis with `sre-agent incidents` and
`sre-agent show <incident-id>`, propose the restart, approve
it by name, and close the incident with a resolved alert.
The checks above run the same way they did for v0.1.0:

```bash
sre-agent evaluate            # 5 of 5 correct, 0 unsafe actions
sre-agent regression-check    # PASS: the scores match the v0.2.0 baseline
sre-agent injection-check     # 8 of 8: hostile text in telemetry changes nothing
sre-agent tier3-check         # 7 of 7 drills
sre-agent security-check      # 10 of 10 probes pass; the findings print on every run
```

## What v0.2.0 does not do — the limits that ship with it

- **A token-less server still has no authentication.** That
  is F-01's remainder by design: with `SRE_AGENT_API_TOKEN`
  set, every route except `/health` requires the token; with
  none set, the server is a local, single-operator demo and
  must stay on the operator's own machine. There is also
  still no per-sender rate limit (F-02's remainder) — intake
  is capped, not slowed.
- **Secret redaction is still a pattern list (F-03).** More
  shapes are caught; a secret with no label and no known
  prefix is not, and the Compose images are still pinned by
  tag, not by digest (F-06). Both findings are recorded as
  improved, not closed, in the security review.
- **No real systems.** Every fix, drill and adapter answer in
  this release still runs on seeded demo data. The live
  adapter backends remain untested against a real Kubernetes
  cluster, Datadog account or Azure workspace, and the Docker
  Compose demo's diagnosis still comes from the seeded data,
  not from its live Prometheus.
- **The shipped server still forgets.** The shipped app uses
  the in-memory store, so its incidents are gone at restart;
  the SQLite store is for servers built in code. A server's
  own stored incidents are not yet fed back to it as memory.
- **No CLI command for the server's approvals.** Live
  approvals are HTTP calls to the server; the CLI keeps the
  in-process `approve-demo`.
- **No `sre-agent halt` command yet.** The halt is a policy
  setting rehearsed by the Tier 3 drills; for the running
  server, which runs fixes only through the approval flow,
  stopping the process is the live halt.
- **No language model.** Diagnosis is still plain rules, on
  purpose. A model backend behind the same report shape is
  Phase 9, off by default when it comes, and it will need a
  fresh security review and its own published scores.
