# v0.1.0 — release notes and demo scenario walkthrough

Released 9 November 2026. This page is two things in one: the
release notes for the first release, v0.1.0, and a walkthrough
you can follow, step by step, through the demo scenario the
release is scored on. Everything below was run again, from
scratch, on the day of the release; the numbers are the numbers
those runs printed, not numbers copied from an older page.

## What v0.1.0 is

The whole v1 line from the plan, working end to end on demo
data:

- Alerts arrive (Alertmanager shape or a simple generic shape)
  and become incidents, with repeat firings counted as
  duplicates and related alerts grouped onto one incident.
- The agent reads evidence with three read-only tools — a
  PromQL metrics question, a log search, and a service status
  check — and writes a diagnosis where every claim points at
  the evidence behind it. It reasons with plain rules and no
  language model, so it runs with no API key.
- Fixes are three pre-written runbooks (restart, scale,
  rollback) for the demo only. A fix runs only after a named
  human approves that exact action (Tier 2), or inside the
  small pre-approved Tier 3 grant for the demo, with drills
  that rehearse the kill switch.
- Memory over past incidents, read adapters for Kubernetes,
  Datadog and Azure Monitor, and a postmortem draft written
  from the incident record.
- The checks that guard all of it: a five-scenario evaluation
  suite, a regression gate, an eight-case prompt-injection
  set, ten security probes, and the full test suite.

## Walkthrough, part A — no Docker, about ten minutes

You need Python 3.11 or newer. In the top folder of the
repository:

```bash
python -m venv .venv && source .venv/bin/activate
pip install -e ".[dev]"
pytest
```

You should see 242 tests pass. If the safety tests in that
run are red, do not use the agent — that rule is in the
operator guide, and it applies to this release too.

### Step 1 — watch a diagnosis happen

```bash
sre-agent diagnose
```

This runs the reasoning loop once on seeded demo data: a
pretend checkout service that is degraded (2 of its 3 copies
ready), with an error metric reading 162 and an error log
line about a payment gateway timing out. The loop asks its
four fixed questions — service status, error logs, the error
metric, the request metric — stores each answer as evidence,
and prints a report whose top cause is "A call that checkout
depends on is timing out" (confidence 0.85, backed by two
evidence records). Every claim in the report names the
evidence and the exact query behind it.

### Step 2 — the scored scenario, walked through slowly

The release is scored on five set faults. Here is the first
one, pod kill, in slow motion — the other four work the same
way and their scores are in [evaluation.md](evaluation.md).

1. The scenario seeds the demo data the loop reads: the
   checkout service is **down**, with 0 of its 3 copies
   ready and the message "no replicas are ready". The error
   metric reads 0 and the request metric 800 — copies are
   gone, so requests are not even arriving to fail.
2. An incident is opened for checkout in the shop area of
   the demo, and the loop runs its same four questions.
3. The honest answer the evidence supports is narrow:
   copies are missing. The loop's top cause says exactly
   that — "Fewer copies of checkout are ready than wanted,
   so a copy may have failed or be stuck" (confidence 0.65).
4. The scorer checks four things: the outcome (diagnosed),
   the top cause's wording, that every claim cites evidence
   really on the incident, and the unsafe-action count,
   read from the incident record. Pod kill passes all four,
   in 4 steps, with 0 unsafe actions.
5. One limit is printed with the score, not hidden: the
   loop can see copies are missing, but it cannot tell a
   pod kill from any other reason copies are gone — it has
   no tool that could. The scenario is scored only on what
   the loop has a tool to see.

Run the whole suite yourself:

```bash
sre-agent evaluate            # 5 of 5 correct, 0 unsafe actions
sre-agent regression-check    # PASS: the scores match the v0.1.0 baseline
sre-agent injection-check     # 8 of 8: hostile text in telemetry changes nothing
```

### Step 3 — approve a fix, and read its postmortem

```bash
sre-agent approve-demo --by "Your Name"
```

The tool proposes a restart of the demo checkout workload,
the policy engine sends it for approval, and nothing runs
until you type the approval at the prompt. On release day,
approving it printed: the restart ran, the failing state
cleared, the incident ended resolved, and the audit log
held 2 decisions for it — the "needs approval" and the
named approval. Saying no, or closing the prompt, runs
nothing.

```bash
sre-agent postmortem-demo
```

This runs a whole demo incident — diagnosis, an approved
restart, resolution — and prints the postmortem draft
written from that real record: timeline, diagnosis, the
evidence with its queries, the actions, and the audit
decisions, each with the time the record really holds.

### Step 4 — the bounded-autonomy and safety checks

```bash
sre-agent tier3-check     # 7 of 7 drills: the grant holds, the halt stops the second run
sre-agent security-check  # 10 of 10 probes pass; the 8 findings print on every run
sre-agent memory-demo     # past incidents, each runbook's record, suggestions (advice only)
sre-agent adapters-demo   # Kubernetes pods, a Datadog series, Azure rows — all read-only
```

What to look for: in `tier3-check`, rollback is *not*
pre-approved and does not run on its own, and the drill
where the halt is pressed between two runs leaves the
second run refused and the workload untouched. In
`security-check`, the probes are the good news; the
findings printed under them are the honest news, and they
carry into this release — see the limits below.

## Walkthrough, part B — with Docker, the live alert path

On a machine with Docker, [demo.md](demo.md) walks the
live path: `docker compose up --build` starts the pretend
checkout service, Prometheus, Alertmanager and the agent's
server together; `./demo/inject_fault.sh` makes requests
start failing; within about 15 seconds the `HighErrorRate`
alert fires and the incident lands — watch it with
`curl http://localhost:8080/incidents`; and
`./demo/inject_fault.sh off` recovers the service, so the
resolved alert closes the incident.

Stated plainly: this part was **not** run in the release
environment, which has no Docker — the same status the demo
has carried since it was built. The test suite exercises
the sample service's real web routes and checks that the
Compose, Prometheus and Alertmanager files agree with the
code and with each other; the full Compose run stays a
human check on a machine with Docker. Two more honest
notes on this part: the reasoning loop is not wired to the
demo's live Prometheus yet (its tools still read the
built-in demo backends), and the fixes in part A run
against the in-process demo workloads, not against the
Compose sample service.

## What v0.1.0 does not do — the limits that ship with it

- **Keep the server on your own machine.** The webhook
  server has no authentication (finding F-01) and ingestion
  has no size or rate limits (F-02). Both are accepted in
  writing for a local, single-operator demo only, and they
  are the first fixes owed before any shared use. The other
  six findings are in [security-review.md](security-review.md).
- **No real systems.** Every fix, drill and adapter demo in
  this release runs on seeded demo data. No live Kubernetes
  cluster, Datadog account or Azure workspace was called,
  and no live call is claimed as tested.
- **Not wired together yet.** The reasoning loop does not
  run inside the server, approving a live server incident
  is not wired, the read adapters do not feed a live
  diagnosis, and memory's suggestions are reported, not
  fed into one. Each page that describes a piece says so.
- **No `sre-agent halt` command yet.** The halt is a policy
  setting rehearsed by the Tier 3 drills; for the running
  server, which never runs fixes, stopping the process is
  the halt. The operator guide states this plainly.
- **No language model.** Diagnosis is plain rules, on
  purpose: exact to test, free to run. A model backend
  behind the same report shape is future work, and it will
  need a fresh security review when it lands.
